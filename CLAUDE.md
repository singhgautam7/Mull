# Mull

Mull is an offline English (UK) dictionary and vocabulary app for Android, built in
Flutter. Look a word up, or open the Mull tab and swipe through a mix of curated
collections one word card at a time. Everything is local: no account, no sync, no network
call, ever.

**Stack:** Flutter (stable) · Riverpod · GoRouter · Drift (user data) · sqlite3 (read-only
dictionary, FTS5) · shared_preferences · dynamic_color · share_plus (export and
share, hands text to the OS share sheet) · flutter_animate (unused so far).
Package `com.grs.dictionary`, Android only, minSdk 24.

**UI source of truth:** `specs/design/HANDOFF.md` (gitignored, on disk). Read it before
building or changing any screen. Perch at `/Users/gautam/Desktop/Projects/Personal/Perch`
is the read-only reference for how Material 3 Expressive is executed: where HANDOFF.md and
Perch disagree on layout or intent, HANDOFF.md wins; on execution (colour roles, motion
curves, component styling), Perch wins.

## Persistence decision

Perch uses Drift, so Mull's user database is Drift (`lib/core/database/user_db.dart`).
Isar was not considered: the prompt only asks about it if Perch used it, and Perch does
not. The dictionary is a second, separate SQLite file opened read-only through
`package:sqlite3` directly (`lib/core/database/dictionary_db.dart`), because its schema is
owned by the build pipeline, not by Drift codegen. `sqlite3` 3.x bundles SQLite (with
FTS5) through Dart hooks; `sqlite3_flutter_libs` is obsolete and must not be added.

## Data rules

The previous attempt at this app failed on exactly these points. They are hard
constraints, not suggestions.

**D1. No network in the data path. Ever.** No dictionary API. No online fallback. No
"enrichment" fetch. If a word is not in the shipped dataset, it does not exist in the app.
There is no HTTP client in `pubspec.yaml` and the app declares no `INTERNET` permission.
If a future feature needs a dictionary update, it downloads a single versioned file with a
checksum, never a per-word request.

**D2. Ship a prebuilt SQLite file. Never seed a database at first launch.**
`assets/db/dictionary.db.gz` is gunzipped and copied to application support directory on
first run. This is a decompress-and-copy, not a parse-and-insert. Target under 3 seconds
on a mid-range device. Show the HANDOFF.md first-run state while it happens. Store the
shipped `dict_version` in prefs and re-install the asset only when the bundled version is
newer.

**D3. Two databases. Never one.**
- `dictionary.db`: read-only, opened in read-only mode, never written to by the app. Has a
  `meta` table with `dict_version`, `built_at`, `source_attribution`. Replaceable
  wholesale on app update.
- User DB: notes, bookmarks, custom lists, seen-state, stats, settings.

A dictionary replacement must never be able to touch user data. A user-schema migration
must never be able to touch the dictionary. Enforce this with two separate repository
classes that do not share a connection.

**D4. User data references words by a stable string key, never a row id.** Key format:
`{headword_norm}|{pos}|{sense_index}` e.g. `abate|verb|1`. Generated by the build
pipeline, stored in the dictionary DB as an indexed column, and stored in user records as
a plain string. When dictionary v2 ships with rebuilt row ids, every bookmark and note
must still resolve. Add a test that proves a bookmark survives a simulated DB swap.

**D5. Search is FTS5.** `words_fts` virtual table over headword + definition. Plus a
normalised, indexed `headword_norm` column (lowercased, diacritics stripped, no
punctuation) for exact and prefix lookup. Search order: exact → prefix → FTS → trigram
fuzzy fallback for typos. Search must return in under 50ms on a mid-range device with the
full dataset loaded.

**D6. The dictionary is built by a script, not by the app.** See
`tools/build_dictionary/`. The app never transforms dictionary data at runtime.

## Collections and the mix

- Everything is a collection, read through one query (`collectionsProvider`). `band`,
  `topic`, `idiom` and `pairs` live in the dictionary; `system` (Bookmarks, From my reading)
  and `user` rows live in the user DB (`user_collections`, `user_collection_words`, schema 3)
  and are joined in by the provider layer. Their slugs are `bookmarks`, `reading`, `u{n}`;
  a mix source, a route (`/collection/{slug}`, `/mull?scope={slug}`) and the seen-progress
  map all take any slug. There is no Lists screen and no separate lists model.
- The pre-3 tables (`bookmarks`, `word_lists`, `list_words`) were copied into the unified
  model by the schema 3 migration and are retained, unread, until that migration has proven
  itself on real installs. Drop them a release later, never in the same release.

- Two datasets in one `words` table: the lookup dictionary (~136k headwords, Wiktionary
  text, no curation) and the learning set (`in_learning_set = 1`, ~7k words picked by
  prevalence, frequency, age of acquisition and concreteness, definitions LLM-rewritten and
  QA-gated). Only learning-set words enter collections and the mix.
- Collections have two axes: band is derived from `prevalence`, topic collections from the
  LLM topic tags and the norms (`topic_collections()` in the pipeline). Never merge the two
  code paths. Idiom collections hold `idiom_key`s in `collection_words`; the `pairs` kind is
  hidden by the app until Design ships a two-word card.
- The Mull tab plays a **mix**, never a collection. Scoped play from a collection card is
  a temporary override (`MixSpec.scoped`, `app_state.last_scoped_collection`) and must
  never mutate the active mix.
- The spaced repetition system is the interval ladder (`[1, 3, 7, 21, 60]` days by
  `seenCount`) and the seen-policy ratio (`unseen_only` 100/0, `light` 85/15, `mixed`
  70/30, `review_only` 0/100 due-first). That is all of it. Do not add SM-2, FSRS, ease
  factors, or grading.
- Seen is written on card exit after the dwell threshold (`kSeenDwellThreshold`, 1.2 s),
  never on entry.
- Queues are 30 cards, extended near the end, deduplicated by `word_key`, never
  persisted; the mix is.
- `word_tags` is retained deliberately even though v1 does not read it.
- Four presets (Anything, Quick wins, Stretch me, Review) are created on first run, not
  editable, duplicable. Their sources are refreshed on every dictionary install.

## Theme rules

- One source of truth: `lib/core/theme/`. A `ThemeFamily` derives every role in oklch into
  `MullColors`; `AppTheme` builds one cached `ThemeData` per (family, tone). No hardcoded
  colours anywhere. No orphaned tokens. A hex value outside the token file is a bug.
- Read colours as `context.colors.<role>`, type as `MullType.<step>`, everything else from
  `Space`, `Radii`, `IconSpec`, `Motion`.
- Dynamic colour takes one wallpaper seed and derives the family at Mull's chroma (0.11).
  Fixed hues (list swatches) are stored as an index into `MullColors.tagHues` and
  re-derived per theme.
- The Mull tab background is AMOLED black in dark mode and pure white in light mode,
  regardless of family or the AMOLED toggle (`MullColors.lingerSurface`). Cards keep
  `surfaceContainer`. Entering and leaving is animated through `LingerBackground`, never a
  hard cut.
- Motion: Perch's curves and durations. Spring for finger-caused, decelerate for
  system-caused. Honour reduced motion via `Motion.of` / `Motion.curveOf`.
- One typeface, Instrument Sans, bundled. Weights must move the `wght` axis
  (`MullType` does; `.weight(n)` for one-offs). No serif. Headword step by grapheme count.

## Known gotchas

- Seven taps on the version line under More opens the debug route.
- The Mull tab's overflow offers "Open full entry" and "Progress"; "Show me fewer like
  this" from HANDOFF 3.2 is not implemented (there is no signal to act on yet).
- Word of the day notifications are a setting only; no scheduling plugin is wired.
  Adding one needs `flutter_local_notifications` and core library desugaring.
- List reorder by drag (HANDOFF 3.7) is not implemented; `reorderList` exists in the
  repository for when it is.
- The committed dictionary is the full lookup build (~49 MB gzipped, ~127 MB installed).
  The learning-set definitions need stage C of the pipeline (an API key) to be the
  rewritten ones; a `--wiktionary-fallback` build keeps Wiktionary text and says so.
- Pronunciation is a method channel to Android's `TextToSpeech` in `MainActivity.kt`, not a
  plugin: `flutter_tts` applied the Kotlin Gradle Plugin, which Flutter is deprecating.
- The icon art is drawn to the board's numbers in `tool/generate_icons_test.dart`, with the
  mark set in JetBrains Mono (`tool/fonts/`, OFL). Re-run the tool, then the two generators.
  The monochrome layer is a stencil (solid page, the spine, mark and ribbon cut out) drawn
  1.45x larger than the colour book: Android keeps only its alpha and launchers draw themed
  icons smaller. A monochrome drawn like the colour layers renders as a blank book.
- Text never has a fixed height. The word card body flexes (a long definition steps the
  headword down one size, then the body scrolls, the action row is pinned) and
  `test/ui/font_scale_test.dart` renders every screen and sheet at the largest OS font scale
  on a 360dp phone; a RenderFlex overflow fails it.
- Riverpod 3 moved `Override` to `package:flutter_riverpod/misc.dart`.
- `dynamic_color` 2.x builds `material_ui` ColorSchemes, not Flutter's; Mull reads only
  the `CorePalette` seed via `DynamicColorPlugin.getCorePalette()` (deprecated upstream,
  still the only seed API) and derives the rest itself.
- Tests run real isolates and real sqlite: use `tester.runAsync` around anything that
  installs or opens a database in a widget test.
- HANDOFF 1.4 lists the headword steps at weight 400 in the table but says twice that
  display sizes take 600 with -0.022em tracking; the code follows the rule text.
