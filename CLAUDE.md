# Mull

Mull is an offline English (UK) dictionary and vocabulary app for Android, built in
Flutter. Look a word up, or open the Mull tab and swipe through a mix of curated
collections one word card at a time. Everything is local: no account, no sync, no network
call, ever.

**Stack:** Flutter (stable) · Riverpod · GoRouter · Drift (user data) · sqlite3 (read-only
dictionary, FTS5) · shared_preferences · dynamic_color · share_plus (export and
share, hands text to the OS share sheet) · file_picker (import: JSON and CSV through the
storage access framework) · csv (shelf CSV and pasted tables) · pdf (the printed shelf
sheet) · flutter_animate (unused so far).
Package `com.grs.dictionary`, Android only, minSdk 24.

**UI source of truth:** `specs/design/mull-design-language/project/specs/design/HANDOFF.md`
(gitignored, on disk). Read it before
building or changing any screen. Perch at `/Users/gautam/Desktop/Projects/Personal/Perch`
is the read-only reference for how Material 3 Expressive is executed: where HANDOFF.md and
Perch disagree on layout or intent, HANDOFF.md wins; on execution (colour roles, motion
curves, component styling), Perch wins.

## Persistence decision

Perch uses Drift, so Mull's user database is Drift (`lib/core/database/user_db.dart`).
Isar was not considered: the prompt only asks about it if Perch used it, and Perch does
not. The dictionary is a second, separate SQLite file opened read-only through
`package:sqlite3` directly (`lib/core/database/dictionary_db.dart`), because its schema is
owned by the build pipeline, not by Drift codegen. `sqlite3` 3.x bundles SQLite (with
FTS5) through Dart hooks; `sqlite3_flutter_libs` is obsolete and must not be added.

## Data rules

The previous attempt at this app failed on exactly these points. They are hard
constraints, not suggestions.

**D1. No network in the data path. Ever.** No dictionary API. No online fallback. No
"enrichment" fetch. If a word is not in the shipped dataset, it does not exist in the app.
There is no HTTP client in `pubspec.yaml` and the app declares no `INTERNET` permission.
If a future feature needs a dictionary update, it downloads a single versioned file with a
checksum, never a per-word request.

**D2. Ship a prebuilt SQLite file. Never seed a database at first launch.**
`assets/db/dictionary.db.gz` is gunzipped and copied to application support directory on
first run. This is a decompress-and-copy, not a parse-and-insert. Target under 3 seconds
on a mid-range device. Show the HANDOFF.md first-run state while it happens. Store the
shipped `dict_version` in prefs and re-install the asset only when the bundled version is
newer.

**D3. Two databases. Never one.**
- `dictionary.db`: read-only, opened in read-only mode, never written to by the app. Has a
  `meta` table with `dict_version`, `built_at`, `source_attribution`. Replaceable
  wholesale on app update.
- User DB: notes, bookmarks, custom lists, seen-state, stats, settings.

A dictionary replacement must never be able to touch user data. A user-schema migration
must never be able to touch the dictionary. Enforce this with two separate repository
classes that do not share a connection.

**D4. User data references words by a stable string key, never a row id.** Key format:
`{headword_norm}|{pos}|{sense_index}` e.g. `abate|verb|1`. Generated by the build
pipeline, stored in the dictionary DB as an indexed column, and stored in user records as
a plain string. When dictionary v2 ships with rebuilt row ids, every bookmark and note
must still resolve. Add a test that proves a bookmark survives a simulated DB swap.

**D5. Search is FTS5.** `words_fts` virtual table over headword + definition. Plus a
normalised, indexed `headword_norm` column (lowercased, diacritics stripped, no
punctuation) for exact and prefix lookup. Search order: exact → prefix → FTS → trigram
fuzzy fallback for typos. Search must return in under 50ms on a mid-range device with the
full dataset loaded. Both FTS tables are `detail=none, columnsize=0` and the trigram table
holds one row per headword: no phrase or NEAR queries, ever, only AND-ed `"token"*` prefixes.

**D6. The dictionary is built by a script, not by the app.** See
`tools/build_dictionary/`. The app never transforms dictionary data at runtime.

## Collections and the mix

- Everything is a collection, read through one query (`collectionsProvider`). `band`,
  `topic`, `idiom` and `pairs` live in the dictionary; `system` (Bookmarks, From my reading)
  and `user` rows live in the user DB (`user_collections`, `user_collection_words`, schema 3)
  and are joined in by the provider layer. Their slugs are `bookmarks`, `reading`, `u{n}`;
  a mix source, a route (`/collection/{slug}`, `/mull?scope={slug}`) and the seen-progress
  map all take any slug. There is no Lists screen and no separate lists model.
- A user shelf has a name, an optional note, a colour (an index into `MullColors.tagHues`, null =
  accent) and an icon (a `ShelfIcons` string id, never a code point), schema 5. It is created and
  edited on a full screen (`ShelfEditScreen`, `openShelfEditor`, routes `/shelves/new` and
  `/collection/{slug}/edit`), with icon and colour picked in one sheet (`showIconColorPicker`), and
  drawn everywhere as a `ShelfIcon` disc (tones `MullColors.tagContainer` / `tagOnContainer`).
- The pre-3 tables (`bookmarks`, `word_lists`, `list_words`) were copied into the unified
  model by the schema 3 migration and are retained, unread, until that migration has proven
  itself on real installs. Drop them a release later, never in the same release.

- Two datasets in one `words` table: the lookup dictionary (~136k headwords, Wiktionary
  text, no curation) and the learning set (`in_learning_set = 1`, ~7k words picked by
  prevalence, frequency, age of acquisition and concreteness, definitions LLM-rewritten and
  QA-gated). Only learning-set words enter collections and the mix.
- Collections have two axes: band is derived from `prevalence`, topic collections from the
  LLM topic tags and the norms (`topic_collections()` in the pipeline). Never merge the two
  code paths. Idiom collections hold `idiom_key`s in `collection_words`; the `pairs` kind is
  hidden by the app until Design ships a two-word card.
- The Mull tab plays a **mix**, never a collection. Scoped play from a collection card is
  a temporary override (`MixSpec.scoped`, `app_state.last_scoped_collection`) and must
  never mutate the active mix.
- The spaced repetition system is the interval ladder (`[1, 3, 7, 21, 60]` days by
  `seenCount`) and the seen-policy ratio (`unseen_only` 100/0, `light` 85/15, `mixed`
  70/30, `review_only` 0/100 due-first). That is all of it. Do not add SM-2, FSRS, ease
  factors, or grading.
- Seen is written on card exit after the dwell threshold (`kSeenDwellThreshold`, 1.2 s),
  never on entry.
- Queues are 30 cards, extended near the end, deduplicated by `word_key`, never
  persisted; the mix is.
- `word_tags` lives in the pipeline only (collections are picked from it) and is not
  shipped: the app never reads it and it cost 3.5 MB installed.
- Four presets (Anything, Quick wins, Stretch me, Review) are created on first run, not
  editable, duplicable. Their sources are refreshed on every dictionary install.
- Pre-made shelves (`!collection.isUsers`) are read-only: no + in the header, the overflow has
  no add or import, `AddToShelfScreen` and the import target refuse them. Words added to one before
  November 2026 stay and still show.
- The word sheet's actions are Add to shelf, note, share. Bookmarking is the Bookmarks row of the
  add-to-shelf sheet, whose rows are switches (a word may be on several shelves). Every note is
  listed on More > Notes (`NotesScreen`, `/more/notes`).
- There is no saved mixes page (removed November 2026). Saved mixes are listed and created in the
  mix sheet only; `Routes.playMix` / `?mix=` stay because the Mull tab uses them. The mix tables
  and their export are unchanged, so old exports with saved mixes still import.

## Theme rules

- One source of truth: `lib/core/theme/`. A `ThemeFamily` derives every role in oklch into
  `MullColors`; `AppTheme` builds one cached `ThemeData` per (family, tone). No hardcoded
  colours anywhere. No orphaned tokens. A hex value outside the token file is a bug.
- Read colours as `context.colors.<role>`, type as `MullType.<step>`, everything else from
  `Space`, `Radii`, `IconSpec`, `Motion`.
- Sixteen families: Mull's five (mull, vellum, foxglove, slate, clay), Perch's (perch,
  ember, fern) and Dally's accents (azure, tide, meadow, blush, iris, coral, citron, neon),
  all re-derived at Mull's chroma from their oklch hue. Dally's Ink, Paper and Void are
  Azure in dark, light and true black, which here are tones. The welcome flow is Kuber's
  pattern: one pager of four intro pages (define from any app, ready-made shelves, your own
  shelves, the Mull tab and quizzes) with Kuber's dots, Skip and Next, then one setup page
  (word of the day on/off through `SettingsController.setWotd`, its time, and Light / Dark /
  System; no theme colours there). There is no "where to start" page and no first-run scoped
  play. Every control that changes the theme goes through `ThemeRipple.of(context).run`.
- Dynamic colour takes one wallpaper seed and derives the family at Mull's chroma (0.11).
  Fixed hues (list swatches) are stored as an index into `MullColors.tagHues` and
  re-derived per theme.
- The Mull tab background is AMOLED black in dark mode and pure white in light mode,
  regardless of family or the AMOLED toggle (`MullColors.lingerSurface`). Cards keep
  `surfaceContainer`. Entering and leaving is animated through `LingerBackground`, never a
  hard cut.
- Motion: Perch's curves and durations. Spring for finger-caused, decelerate for
  system-caused. Honour reduced motion via `Motion.of` / `Motion.curveOf`.
- One typeface, Instrument Sans, bundled. Weights must move the `wght` axis
  (`MullType` does; `.weight(n)` for one-offs). No serif. Headword step by grapheme count.

## Data, quiz and platform (pass 02)

- JSON export is `mull.export` format_version 2 (1 still imports), word and phrase keys only
  (rule D4), the dictionary never. Version 2 adds a shelf's `icon` and `note`; a phrase note is a
  row in `notes` keyed by its phrase key, exported like a word note.
  Import parses and previews first, then writes in one transaction. Merge never overwrites a
  note: an existing note keeps its text and the imported one is appended under
  `DataTransferRepository.importedNoteMarker`. Mixes merge by name so presets are not doubled.
  Unresolved word keys are kept and counted, not dropped.
- Word import (`/shelves/import`, or `?target={slug}` from a shelf) parses TSV/CSV/bare lists
  through `ImportTable` (pure, tested), matches through `DictionaryDb.batchMatchWords`
  (exact → alias → lemma → trigram, batched 250 a query), and ends on the review screen.
  Not-found rows are listed and never added, so there is no fallback-definition column.
- The quiz is opened from a shelf overflow only, needs `QuizScreen.minimumWords` (10), writes
  `quiz_sessions` / `quiz_answers` and never `seen`. Distractors: same POS, band within one,
  shelf first, no synonym either way, similar definition length. Cloze blanks inflections
  through `QuizEngine.inflectionPattern`. "Words I got wrong" is the `quiz_wrong` mix source.
- Arrivals: `PROCESS_TEXT`, `ACTION_DEFINE` and `SEND` land in `DefineActivity`, a translucent
  activity in the caller's task (`excludeFromRecents`, standard launch) that runs the
  `defineMain` entrypoint (`lib/define_main.dart`): a see-through host that pulls the arrival
  once the dictionary is open, shows the sheet, and calls `finish` when the last sheet is gone
  (`_FinishWhenEmpty`). It never opens the app. "Search Mull for it" goes
  through `PlatformSurfaces.go`, which is the router inside the app and `openInApp` (start
  `MainActivity` on a route in its own task, finish the sheet) inside the define host. Both
  activities take their engine from the process's `FlutterEngineGroup` and destroy it with
  the activity. One word opens its sheet; longer text keeps only the sentence around the word
  (`PlatformSurfaces.sentenceAround`); exactly one uncommon word opens directly, otherwise the
  picker offers learning-set and rarer-band words. `sourceHint` is the referrer package
  (`DefineActivity` writes it into the intent before reading it back), shown formatted, never
  raw. `MainActivity` only ever receives a widget tap (`word_key`) or a hand-off (`route`).
- Widget: Dart writes a 30-day `widget.schedule` to prefs; the Kotlin provider picks today's
  entry, so it rolls over daily and survives a reboot without the app. Colours live in
  `res/values*/widget_colors.xml` (light, night, and Android 12 dynamic via `system_*`).
- Backup: only `app_flutter/mull_user.sqlite` (domain `root`) is included; naming one include is
  what excludes the dictionary, and lint rejects an `<exclude>` outside an include. Verified
  with `bmgr backupnow` on an emulator: 135 KB measured, dictionary.db absent.
- The widget needs no boot receiver (the system re-sends `APPWIDGET_UPDATE`); the
  reminder's alarm does, which is why `RECEIVE_BOOT_COMPLETED` is declared.
- Main-isolate budget: the dictionary's indexed queries are sub-millisecond and stay
  synchronous. Anything that loops over many rows goes through `DictionaryDb.compute`, one
  long-lived worker isolate per open dictionary with its own read-only connection (its page
  cache stays warm between keystrokes): search per keystroke (`searchAll`, debounced
  `kSearchDebounce` = 100 ms in the Search tab and the add-to-shelf picker), quiz generation
  (`QuizEngine.generator`), and word matching (`matchWords`). Build the closure you hand to
  `compute` in a synchronous function: one made inside an `async` method captures that
  method's completer and cannot be sent. An in-memory test dictionary runs `compute` inline,
  so only `test/database/off_main_isolate_test.dart` (real asset, real worker) proves a
  closure is sendable; add a case there for any new `compute` caller.
- `LoadingHairline` waits the HANDOFF's 120 ms on its own; pass `visible` for the whole load.
  Shelves hold `SkeletonCard` / `SkeletonRow` placeholders until the user streams emit; the
  Mull tab serves the first card before hydrating the rest of the batch.

## Known gotchas

- Seven taps on the "Made with love in India" line under More opens the debug route. The
  version shown beside About comes from the package (`PlatformSurfaces.appVersion`), never a
  string in Dart; bump `pubspec.yaml` only. The privacy screen renders `PRIVACY_POLICY.md`
  from the bundle: edit the file, not the screen.
- The Mull tab's overflow offers "Open full entry" and "Progress"; "Show me fewer like
  this" from HANDOFF 3.2 is not implemented (there is no signal to act on yet).
- Word of the day notifications are native, no plugin: `WordOfDayReminder.kt` arms one
  inexact `AlarmManager` alarm (10-minute window, so no `SCHEDULE_EXACT_ALARM`) from the
  saved `wotd.*` prefs; `ReminderReceiver` posts today's entry from the same `widget.schedule`
  the launcher widget reads and re-arms tomorrow, and re-arms after boot and app update.
  `SettingsController.setWotd` asks for `POST_NOTIFICATIONS` first (declined, the setting
  stays off) and then calls `PlatformSurfaces.scheduleReminder`; the app also re-arms on
  every launch. The two permissions in the manifest are `POST_NOTIFICATIONS` and
  `RECEIVE_BOOT_COMPLETED`; still no `INTERNET`. `PRIVACY_POLICY.md` lists them.
- The emulator on this Mac is arm64 (Apple Silicon): build with
  `--target-platform android-arm64`, and `--profile` when a debug APK is too big to install.
- List reorder by drag (HANDOFF 3.7) is not implemented; `reorderList` exists in the
  repository for when it is.
- The committed dictionary is the full lookup build (36 MB gzipped, 95 MB installed).
  The learning-set definitions need stage C of the pipeline (an API key) to be the
  rewritten ones; a `--wiktionary-fallback` build keeps Wiktionary text and says so.
- Pronunciation is a method channel to Android's `TextToSpeech` in `MainActivity.kt`, not a
  plugin: `flutter_tts` applied the Kotlin Gradle Plugin, which Flutter is deprecating.
- The launcher icon, monochrome layer, notification glyph and splash art come from the icon
  family in `specs/design/app-icon/` (see its `icon.md`): the SVGs are converted to vector
  drawables in `res/`, and the legacy and splash PNGs are rendered from the same SVGs.
- Text never has a fixed height. The word card body flexes (a long definition steps the
  headword down one size, then the body scrolls, the action row is pinned) and
  `test/ui/font_scale_test.dart` renders every screen and sheet at the largest OS font scale
  on a 360dp phone; a RenderFlex overflow fails it.
- Riverpod 3 moved `Override` to `package:flutter_riverpod/misc.dart`.
- `dynamic_color` 2.x builds `material_ui` ColorSchemes, not Flutter's; Mull reads only
  the `CorePalette` seed via `DynamicColorPlugin.getCorePalette()` (deprecated upstream,
  still the only seed API) and derives the rest itself.
- Tests run real isolates and real sqlite: use `tester.runAsync` around anything that
  installs or opens a database in a widget test.
- HANDOFF 1.4 lists the headword steps at weight 400 in the table but says twice that
  display sizes take 600 with -0.022em tracking; the code follows the rule text.

### Things that get worse as data grows (audit, September 2026)

Found on the full dictionary in a profile build (arm64 emulator; a mid-range phone is
roughly 3x slower), fixed in the same pass. The rule after each is what keeps it fixed.

- **A dictionary query in `build()` runs on every rebuild, and rebuilds come from streams
  you do not see.** The shelf screen used to materialise all 1,599 rows inside `build()`
  (110 to 167 ms cold) on every `setState`, including the scroll-direction toggle of the Mull
  button. Now `shelfEntriesProvider(slug)` (autoDispose family) reads them once per change of
  the shelf's keys and the picker reuses it. Rule: read the dictionary in a provider or
  `initState`, never in `build()`; a rebuild may only sort and filter what is in memory.
- **Every column the app filters by is indexed in `schema.sql`.** `aliases` had no index on
  `word_key`, so `usSpelling()` and `inflections()` scanned 220k rows (8 ms host, 40 ms or
  more on a phone) per word sheet build. Rule: `EXPLAIN QUERY PLAN` a new query and reject
  `SCAN` on any table over a few thousand rows.
- **Search is debounced and off the UI isolate.** It was three synchronous queries per
  keystroke: p50 5.5 ms, p95 23 ms, first FTS hit of a session 120 to 180 ms. Rule: nothing
  joins the keystroke path without the debounce and without going through `compute`.
- **Providers that hold a table are `autoDispose`.** `_noteProvider` / `_contextsProvider`
  (one live Drift watch per word ever opened) and `statsProvider` (re-reads the unbounded
  `seen_events` log on every seen change) were not. Rule: a `.family` keyed by a word, and
  anything that reads a whole table, is `autoDispose`.
- **To let a frame land, await `WidgetsBinding.instance.endOfFrame`**, not
  `Future.delayed(Duration.zero)`: the timer fires before the frame (measured: the Mull tab
  hydrated its other 29 cards 11 ms before the first card's frame).
- **Anything that loops over the learning set runs on the worker.** Quiz generation was a
  synchronous burst (4.8k candidates, a sort per question).
- **Never let an arrival start a second `MainActivity`.** `singleTop` only reuses the top of
  the target task; a `PROCESS_TEXT` from another app lands in *that app's* task, so it created a
  new `MainActivity` instance, a new engine and a second run of `main()` in Mull's process. The
  launch transition then held the whole display for 5 s waiting for a first frame
  (`BLASTSyncEngine: Sync group timeout`), PSS reached 580 MB with two engines and `lmkd` began
  killing other apps. That was the "Define in Mull freezes the phone" bug of September 2026.
  Rule: intents from outside go to `DefineActivity`; never add an arrival intent filter to
  `MainActivity`. A Dart entrypoint in its own library must be imported from `main.dart` (or
  AOT drops it) and started with its library URI (`package:mull/define_main.dart`), or the
  engine logs `Could not resolve main entrypoint function` and draws nothing.
- **A debug build is not a device test for start-up.** In JIT a second engine loads the 123 MB
  kernel again and takes seconds to its first frame; release takes ~90 ms. Measure launch and
  arrival paths on a release APK.
- **Platform-thread work in `MainActivity` is lazy.** `TextToSpeech` was bound, with
  `setLanguage`, in `configureFlutterEngine`; a slow engine there during a cold start is the
  one thing on the platform main thread that can be a real ANR (a stalled Dart isolate is a
  frozen frame, not an ANR). It now binds on the first speak.
- **Still open, by design for now:** `seenMapProvider` streams the whole `seen` table on
  every `markSeen` and `collectionProgressProvider` recounts every collection against it
  (about 8k map lookups per swipe, sub-millisecond, bounded by the learning set).
  `seenStates()` binds one parameter per key; SQLite's limit is 32,766, so a 33k-word
  imported shelf would still throw there. `statsProvider` reads the whole `seen_events` log
  across the Drift isolate on every open; the loop is trivial but the transfer grows with
  use, and only `perDay` could be narrowed to 30 days (the heatmap and the longest run need
  all of it). Rule: derive from what is already in memory when a user table changes; chunk
  any new `IN (...)` over 250 keys as `_inChunks` and `_exists` do; compute aggregates in
  SQL, never by reading rows into Dart.

### Things that get worse as data grows (audit, 29 September 2026)

Measured on the full dictionary, host and a profile build on the arm64 emulator. The rule
after each is what keeps it fixed.

- **A synchronous `Provider` first watched in `build()` runs *in* that build.** The rule
  above ("read the dictionary in a provider, never in `build()`") is not satisfied by being
  a provider: a plain `Provider` computes lazily on first watch, which is inside the frame
  that watched it. `shelfKindsProvider` was 44 `IN (...)` queries and the whole **69.1 ms**
  first build of the Shelves tab; `collectionKeysProvider` was 27 queries and 8,084 key
  strings, **22 ms**, and was Home's **85.9 ms** first build. Both now answer in **0.09 ms**
  because the reading moved to a `FutureProvider` over `DictionaryDb.compute`
  (`dictionaryCollectionKeysProvider`, `shelfEntriesProvider`, `wordEntries`,
  `collectionWordKeysAsync`) with a synchronous facade that yields an empty map for a frame.
  Rule: if a provider loops over rows, it is a `FutureProvider` backed by `compute`; if
  callers need a plain value, give them a facade that falls back, and a `…SettlingProvider`
  for the screens to hold their shape with.
- **Derive from the schema's invariant instead of asking per row.** A dictionary shelf's
  kind already settles what is on it (`band`/`topic` hold words, `idiom` holds phrases), so
  `shelfKindsProvider` asks nothing of the 22 dictionary shelves and only the user's own.
  `test/database/shelf_kinds_test.dart` holds the shipped dictionary to it, because the
  failure would otherwise be silent. Rule: an invariant the pipeline guarantees may be
  assumed in the app only with a test against the shipped dictionary.
- **`ListView(children: [...])` builds every child, however the data is paged.** The Shelves
  tab constructed all 27 shelf cards on open: once the queries were off the frame, that was
  the entire **39 ms** that remained, with four cards on screen. It is now a
  `CustomScrollView` whose topics are a `SliverList.separated` over `TwoColumnGrid.row`
  pairs (**about 20 ms** on the emulator, most of it first-time text layout). Rule: any list
  whose length grows with the data is a builder or a sliver, never a child list. The Mull
  tab's `PageView.builder` already was: `test/linger/lazy_cards_test.dart` pins it at one
  card in the tree on open and after three pages, against a 200-word pool.
- **A loader that flashes is worse than no loader.** A warm start drew `InstallScreen` for
  one frame while the already-installed dictionary opened, which read as a glitch. `Delayed`
  (`shared/widgets/states.dart`, 250 ms) renders nothing until the work has actually taken a
  moment; `LoadingHairline` keeps its own HANDOFF 120 ms. Rule: every loading state is behind
  `Delayed` or `LoadingHairline`, and where there is something honest to show meanwhile
  (a card whose count the dictionary already knows) that is the `placeholder`, not a
  skeleton. The native splash already holds to Flutter's first frame; what it handed over to
  was the problem.
- **The mix chip has one appearance and no view-dependent state at all.** HANDOFF 11.2 used
  to fill it `surfaceContainerHigh` at 78% and drop it to 0.34 opacity after the first
  swipe. Both were faults. 0.34 is inside Material's disabled range (0.38), so a live
  control read as unavailable; and the fill made an opaque pill 8dp above the pager's clip
  edge (`Positioned.fill(top: pad.top + 96 - 34)`), so a card swiping out was guillotined
  directly under it and the pair read as a card sliding behind a header. The chip sits
  entirely above the viewport and never has anything drawn under it, so the fill bought
  nothing else. It is now unfilled and constant: no opacity, no scale, no `_chipFaded`.
  **HANDOFF 11.2 was rewritten to match (30 September 2026)**, so the code and the handoff
  agree; do not reintroduce the fade from an older copy of the spec. Rule: an ordinary
  control does not change appearance because the view scrolled, and nothing floating over
  the Mull tab's pager carries a fill it does not need. The clip edge itself is inherent to
  a vertical pager and stays.
- **Rules v2 for Dictionary Definitions and Permanent Build QA Gate.**
  Dictionary definitions must adhere to Rules v2:
  - R2: Words in `definition_short` must be plain, everyday vocabulary (top 3,000 frequency lemma rank), never harder than the headword itself.
  - R3: No circular definitions (e.g. defining *whimsical* as "given to whimsy", or *insolently* as "in an insolent manner").
  - R4: No long em-dashes, hyphens, brackets, or formatting artifacts.
  - R6: Strict length constraints (`definition_short` <= 14 words; `example` between 8 and 18 words containing the headword).
  `build_dictionary.py` integrates a permanent QA gating check (`tools/build_dictionary/qa_definitions.py`) running over all learning set rows immediately after database emission: any rule violation aborts the build with a non-zero exit code before `assets/db/dictionary.db.gz` is compressed. All rewrites are cached deterministically in `tools/build_dictionary/work/llm_cache.jsonl`.

### Things that get worse as data grows (audit, 23 November 2026)

Measured with `integration_test/perf_test.dart` (profile, full dictionary, a seeded user DB: 5 shelves, one of
1,500 words, 300 bookmarks and notes, 9,000 seen events). Numbers and method: `specs/app-polish-2/performance.md`.

- **A tab switch animates only the incoming tab, inside its own layer.** The old slide translated the whole shell
  with the `RepaintBoundary` outside the transform, so the tab repainted every frame of the slide. Kuber's
  PageView shell was measured and rejected: its far-tab jump lays out a third page in the jump frame (build worst
  9.8 → 30.9 ms). Rule: put the `RepaintBoundary` *inside* any transition that moves a large subtree, and never
  make a tab switch relay out pages that are not the destination.
- **A synchronous `Provider` that touches the dictionary is a first-frame cost, even for one value.**
  `wordOfTheDayProvider` built its pool (a DISTINCT join, about 100 ms on the emulator) inside Home's first build;
  More ran `count(DISTINCT headword_norm)` over 136k rows in `build()`. Both are `compute` now (Home's first-build
  worst 310 → 42 ms, More 72 → 20 ms). Rule: anything that is not a point lookup by an indexed key is a
  `FutureProvider` over `DictionaryDb.compute`, whatever it returns, with a case in `off_main_isolate_test.dart`.
- **Nothing heavy in the first frame's post-frame callback either.** The widget schedule (30 picks and a
  `jsonEncode`) ran there; it runs on the worker. A warm start no longer cross-fades two whole MaterialApps over
  Home's first build (`_fadeIn` in `app.dart`: only when the install state actually showed).
- **Watch values with equality, at the leaf.** `Progress` has `==`; `progressOfProvider(slug)` (a select),
  `inProgressSlugsProvider` (`SlugSet`) and `continueSlugProvider` notify only on a real change. Rule: a screen's
  `build()` never watches `seenMapProvider`, `collectionProgressProvider` or an `AsyncValue` whole for a flag
  (`select((v) => v.isLoading)`); the widget that draws a number watches that number. Home is section consumers.
- **Offstage tabs do not rebuild** (Riverpod 3 pauses subscriptions under a disabled `TickerMode`, and go_router
  puts offstage branches under one; measured: 0 rebuilds of Home or Shelves over Mull-tab swipes that write seen,
  on main too). The cost of a broad watch is on the visible screen and on the return to a tab.
- **`ref.watch(settingsProvider)` whole is for settings screens only.** The app root watches a record of the theme
  inputs and text size; every other screen and sheet selects its fields.
- **Home lists at most six of your shelves** (`HomeScreen.yourShelvesShown`); the Shelves tab lists them all
  lazily.
- **Emulator raster is not a phone.** On the API 36 AVD every full-screen frame rasters at 15 to 20 ms through GPU
  translation, so "frames over 16 ms" there is raster noise; the API 30 AVD (`Kuber_LowEnd`, 2 cores) showed 0
  frames over 16 ms on tab switches and scrolls with the same build. Judge build times on the emulator and raster
  on a device.

### Round 3 of pass 2 (23 November 2026)

Measured with `integration_test/perf_feel_test.dart` (the two paths users feel first; the older harness
never opened a shelf's own menu and never tapped a tab it had not warmed).

- **`showMenu` is not used.** It fades every row in by itself (a shelf's 17 rows were 17 offscreen layers on
  every frame, the last row legible only at the end of the spring) and lays the rows out twice. `showAppMenu`
  is its own `PopupRoute`: one panel, one 150 ms fade, an 8 dp drop. Rule: never animate menu rows one by one.
- **Shelves, Search and More are built before their first visit** (`StatefulShellBranch.preload` + `WarmTab`,
  which waits for idle and paints the tab once unseen). A tab built offstage must not depend on `TickerMode` through `valuesOf` in its build
  (use `getValuesNotifier`), or the first visit rebuilds all of it.
- **Tabs slide as Kuber's pager does** (`BranchStack`: 300 ms ease in and out, both pages side by side, a drag
  follows the finger, the same at Subtle). Not a `PageView`: it lays out a third page on a far jump and cannot
  prepare a page ahead of its visit. This replaces the 6% slide and fade above.
- **An animation's clock starts after the frame that builds its content.** Started on push or on the index change, a
  heavy first frame (the word sheet's was 28 to 126 ms) eats the fastest part, so it pops. `_SheetRoute` and
  `BranchStack` wait for `endOfFrame`. A long word entry builds only what fits until the sheet has opened.
- **There is no Motion setting** (removed November 2026; a stored `motion.preference` is ignored). The level is the
  phone's: Off under Remove animations, Subtle under 3.5 GB of RAM, else Expressive. The API 36 AVD has 2 GB, so it
  is Subtle unless `motion.deviceClass` is set to `normal`.
- **Never tween a fill from `Colors.transparent`**: it is black at alpha 0, so the fade goes through dark grey
  (the filter pills' flicker). Use the target colour at alpha 0. A filter change keeps what stays (keyed by its
  slug or word key) and eases in only what appears (`StaggeredEntrance`); it never blanks the list.
- **No ink sparkle on anything whose own fill changes** (chips, segmented toggle): it lay over the new fill for
  about a second and read as a flicker. `pressedLayer` is the state layer.
- **Nothing in a chip row pops its width.** The count badge grows and shrinks with the selection.
- **Read `HeaderPage.insetOf` below `HeaderPage`.** Read above it, it is 0: that hid the whole Search field,
  and tests with no status bar could not see it.
